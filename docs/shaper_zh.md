# Shaper（限速 + 小包优先）

## 作用

下载、上传或游戏更新跑满线路时，数据包会在光猫、路由器或运营商设备里排队（bufferbloat）。这些缓冲区往往有几百毫秒深，游戏包只能排在大流量后面。

Shaper 的思路和路由器上的 SQM（cake / fq_codel）相同：UDPlex 以略低于瓶颈带宽的速率发送，让队列出现在 UDPlex 内部，而不是光猫里。在 UDPlex 内部：

- **小包优先**：游戏、语音、TCP ACK、握手包跳过大流量队列直接发送；
- **大流量队列用 CoDel 控制长度**，让隧道内的 TCP 主动降速，而不是把缓冲区塞满。

隧道两端都是 UDPlex，所以下行方向可以在发送处（服务端）直接限速，效果比家用路由器在入口侧整形好得多。

## 实测效果

测试环境：WireGuard over UDPlex，线路为上行 40 Mbit/s、下行 200 Mbit/s，RTT 20 ms，光猫缓冲 200 ms。探测流量是 60 pps × 100 B 的类游戏流，经隧道发送，在大流量 TCP 传输期间测量。

| | 上传跑满 | 下载跑满 | 双向跑满 | 大流量吞吐 上/下 |
|---|---|---|---|---|
| 不限速 | 约 195 ms | 约 187 ms | 约 205 ms | 36 / 180 Mbit/s |
| 限速为线路的 95% | **约 21 ms** | **约 21 ms** | **约 21 ms** | 35 / 173 Mbit/s |

空闲时延迟约 21–24 ms，也就是说开启 shaper 后，即使线路跑满，游戏延迟也几乎不增加。

## 配置

在经过瓶颈链路发送数据的组件上添加 `shaper`：

- **客户端**的每条 `forward` 线路：`rate` 设为该线路的上行带宽；
- **服务端**的每个 `listen`：`rate` 设为客户端的下行带宽。每个客户端地址分别限速。

```yaml
# 客户端
  - type: forward
    tag: line_a
    forwarders: [SERVER_IP:5900]
    shaper:
      enabled: true
      rate: 38          # Mbit/s，实测上行带宽的 90–95%

# 服务端
  - type: listen
    tag: line_a
    listen_addr: 0.0.0.0:5900
    shaper:
      enabled: true
      rate: 190         # Mbit/s，客户端下行带宽的 90–95%
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `enabled` | `false` | 是否启用 |
| `rate` | （必填） | 发送速率，单位 Mbit/s，包含 IP/UDP 头。建议取实际带宽的 90–95%；如果高于瓶颈带宽，队列会回到光猫里，就没有效果了 |
| `overhead` | `0` | IP 层以下每个包的额外开销（字节），如 PPPoE 为 8 |
| `priority_size` | `1000` | UDP 载荷不超过该大小（字节）的包优先发送。隧道内的大流量使用满尺寸包（约 1400 字节以上），1000 可以可靠地区分两者。设为 `0` 关闭优先 |
| `priority_share` | `50` | 有大流量排队时，保证给优先流量的带宽百分比。超出部分让给大流量，避免小包洪泛把大流量饿死 |
| `target_delay` | `5` | 毫秒，大流量队列的 CoDel 目标时延 |
| `interval` | `100` | 毫秒，CoDel 判定窗口，大致取业务的典型 RTT |
| `queue_limit` | 按 `rate` 计算的 100 ms 数据量（256 KB – 4 MB） | 每条路径最多排队的字节数，满了会丢弃最早的大流量包 |

## Autorate：带宽会变化的线路

固定的 `rate` 只有在线路真能跑到这个速率时才有效。4G/5G、无线桥接、晚高峰拥塞的线路，带宽会掉到 `rate` 以下，队列又回到了光猫里。开启 `autorate: true` 后，shaper 会自动跟随线路带宽：

- 每隔 `probe_interval` 向对端发送一个小探测包，对端测出单向时延后回报。上下行分别测量：客户端调整上行，服务端调整该客户端的下行。两端的时钟不需要同步。
- 单向时延比基线高出 `bloat_threshold` 时，说明线路里的队列在增长，速率降到实际发送量的 90%。
- 线路繁忙且时延保持在低位时，速率逐步回升到 `max_rate`；线路空闲时回到 `rate`。

```yaml
    shaper:
      enabled: true
      rate: 38          # Mbit/s，正常带宽（起始值）
      autorate: true
      min_rate: 8       # 不低于该值
      max_rate: 38      # 不高于该值；带宽有时更高的线路可以设大一些
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `autorate` | `false` | 是否自动调整速率 |
| `min_rate` | `rate`/5 | Mbit/s，下限 |
| `max_rate` | `rate` | Mbit/s，上限 |
| `bloat_threshold` | `15` | 毫秒，单向时延超出基线多少算作队列增长。越小延迟越稳，但损失的带宽越多 |
| `probe_interval` | `50` | 毫秒，线路繁忙时的探测间隔（空闲时每秒一次） |

实测：上传或下载进行中，线路带宽突然减半（上行 40 → 20 Mbit/s，下行 200 → 100 Mbit/s；空闲延迟约 22 ms）：

| | 降速后游戏延迟（p50 / p99） | 降速后大流量吞吐 |
|---|---|---|
| 固定速率，上传 | 181 / 233 ms | 18.6 Mbit/s |
| Autorate，上传 | **20.6 / 37 ms** | 16.5 Mbit/s |
| 固定速率，下载 | 75 / 196 ms | 90.5 Mbit/s |
| Autorate，下载 | **20.7 / 36 ms** | 84.7 Mbit/s |

带宽恢复后，速率会在数秒内回升。

Autorate 要求两端都启用 `auth`，并且两端都是支持该功能的版本。旧版本对端不会回应探测，此时 shaper 保持 `rate` 不变。

## 注意事项

- 鉴权与心跳消息不受限速影响，不会被延迟。
- 限速按路径生效。负载均衡或冗余模式下，请在每条线路上分别按该线路的带宽设置。负载均衡可以用 `qdelay_<tag>` 选择更空闲的线路（参见[负载均衡](load_balancer_zh.md#按排队时延切换线路)）。
- Shaper 只作用于 UDP 的 `listen`/`forward`。`tcp_tunnel_*` 组件有自己的队列管理和 `pacing_rate` 选项，参见 [TCP 隧道调优](tcp_tunnel_tuning_zh.md)。
- CPU 开销很小：单核环境下启用 shaper（速率不构成限制）时，WireGuard 隧道内 TCP 的峰值吞吐下降 1–10%，延迟不变。未启用时（默认）没有任何开销。
- 统计信息（队列时延、丢包、优先包数，以及启用 autorate 时每条路径的当前速率和单向时延）在 `/api/listen/<tag>`、`/api/forward/<tag>` 的返回结果中的 `shaper` 字段。
